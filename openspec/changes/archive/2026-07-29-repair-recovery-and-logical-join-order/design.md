The inherited baseline is source exact `a602149522c7038f29e13307bb925a48ed3848d7`, whose parent docs exact `740373298711002548cbe6eecb3c63dcb045db74` already restores Refresh after terminal join failure. Existing focused/full automated evidence is exact-local and remains useful history. The Owner removed the successful manual-Refresh `Ready to chat` Toast, excluded passive polling from presentation loading, and makes fixed Runtime `AppFeedback` owner `webchat-runtime-readiness` the sole feedback owner for every active Refresh or real connect/join/reattach/host rebuild/recovery operation. Its exact loading copy is `Connected to the chat...`; despite the past-tense wording, the entry remains loading until that logical operation settles. The independent manual-Refresh `Reconnecting to the chat...` producer is deleted. Success dismisses only the fixed owner, while only a logically final failure displays exact copy `Connection failed` with no trailing period.

Six additional causes are already isolated:

1. `ArticoRoomTransport` restarts only when `close` fires while `desiredRooms` is non-empty. If timeout-driven leaves empty the set before `close`, a later `join()` can attach to the retained `disconnected` peer and wait forever for an event that already occurred.
2. `Connection.startAttempt` correctly fences an old same-domain generation, but reports `Domain join superseded` through the ordinary operation-failure path. Application effects convert it into `Room.OnErrorEvent`, and generic Toast displays an internal cancellation as a user failure.
3. Current strict SESSION is `{type,sessionId,presenceId,user}`. A previously unseen remote generation receives receiver-local `clock.now()`, while join eligibility depends on `baselinePeerIds`. If both discovery and SESSION for pre-existing A arrive after B commits, B misclassifies A as a later live join.
4. The content injector puts complete `document.location.href` into comctx tab metadata. The background `TabsProviderAdapter` uses that value in `tabs.query({url})`, and the Offscreen relay later requires complete URL equality. A fragment is an in-document position rather than page-routing identity; treating it as a target key can lose or reject the initial Runtime response. Because content bootstrap waits for `initClient()` before mounting the Shadow UI, the control then never appears.
5. `ClientLease.attach()` wraps `registerPage()` and `attachPage()` in a nominal 15-second poll, but `poll()` checks its deadline only after one attempt rejects. A control-plane request that never resolves or rejects therefore owns no terminal deadline. Recovery has already published `connecting`, so background/Offscreen host replacement, Port/response loss, or lost response correlation can leave both readiness and the stable loading Toast permanent. Concurrent watchdog checks may also reach recovery before one owner is established, and a response that arrives after timeout/detach must not mutate or release a newer lease generation. Conversely, a passive watchdog check suspended beyond its captured wall-clock deadline can resume while still accepted as current, immediately publish `unavailable`, clear its owner, and then let the next five-second check obtain a fresh budget and succeed. That obsolete check is not a logically final connection failure and must have no readiness or frontend settlement authority.
6. Page ping, heartbeat, or Port connectivity is a page-context health observation rather than browser tab lifetime. An inactive, frozen, discarded, or recovering tab can remain open while that observation disappears. Treating it as last-page release can retire a still-live tab's logical presence, while a random page id cannot provide the browser-owned tab identity that the background already receives from trusted sender context and the Tabs API.

Adding a required SESSION field is incompatible with released v2 strict parsers. Keeping a shared World v2 room while moving only Chat would advertise incompatible peers as available. The product therefore needs one clean Chat+World namespace generation boundary.

## Goals / Non-Goals

**Goals:**

- Keep failed-join Refresh available and single-flight through the existing request lifecycle, while disabling and rotating the Refresh control for the sole current Runtime readiness loading owner.
- Guarantee that fresh room demand can create one replacement for an already disconnected Artico peer.
- Keep newest-wins attempt fencing while making expected supersession non-user-visible and state-safe.
- Restore the first-version rule that only a remote logical join later than the local logical join can create a remote join notice.
- Keep one logical generation's `presenceId` and `joinedAt` stable through physical recovery.
- Isolate v3 Chat and World peers cleanly from v1/v2 without compatibility code.
- Make content-page RPC targeting fragment-insensitive without weakening exact-tab or real-navigation stale-response safety.
- Keep direct-hash startup, hash-only navigation, and hash changes during initial handshake on one mounted control and logical presence.
- Bound each ClientLease register/attach RPC and the complete startup/recovery generation, single-flight overlapping recovery signals, and reject late lifecycle/request work.
- Make the background Tabs API registry the sole physical tab-lifetime authority: one host owns many exact tabs; close, lost eligibility, or Runtime-domain change releases an old binding, while inactivity or connectivity loss does not.
- Keep trusted `tabId`, document generation, and logical session/presence identity separate; reconstruct still-eligible tab bindings across host replacement without false join/leave.
- Show the sole owner-scoped `Connected to the chat...` loading entry throughout every current Refresh or actual connect/join/reattach/host rebuild/recovery operation, including healthy retained-Runtime reattachment, while ensuring current success dismisses it and only a logically final failure with no current automatic continuation or handoff capable of succeeding replaces it with exact copy `Connection failed`; passive polling or a health probe that has not promoted into such an operation shows none and leaves Refresh unchanged.
- Delete the independent manual-Refresh `Reconnecting to the chat...` producer, end every successful connection operation by dismissing only the fixed Runtime readiness owner, and prevent all intermediate attempt, stale-deadline, and superseded-generation failures from flashing terminal error before later success.
- Accept only one cumulative final exact containing all seven repairs.

**Non-Goals:**

- No unbounded provider retry loop, presentation-owned connecting watchdog, custom background-worker keepalive/wake fallback, or global Runtime restart.
- No suppression of real Artico, Runtime, join, persistence, or protocol errors from diagnostics or their owning non-connection surfaces; connection presentation is deliberately deferred until the logical operation is terminal.
- No ChatMessage, history, reaction, SESSION_END wire-shape, World payload, codec algorithm, limits, or MessageStore/database change.
- No `ChatRoomExtern` method/type expansion, new presenter, second connection feedback owner, Toast geometry, panel-state, alternate bootstrap/status UI, Ready/status result, or browser-specific business branch.
- No fragment-specific room, tab binding, document generation, user-visible navigation state, remount, reconnect, join/leave, or protocol field; no payload-supplied tab identity or tab-id-as-session shortcut.
- No v2 decoder, optional `joinedAt`, dual schema, dual publication, room bridge, local-data migration, package/app version, tag, or release-metadata change.
- No claim of globally trusted total order under arbitrary cross-device clock skew.

## Decisions

### 1. One cumulative route inherits the Refresh repair

`a6021495` is the inherited Refresh baseline. Current authority exact `5cc4e597abf1f9c540b81bf5738fd0f7d1e7a86d` is the sole parent for this replacement docs authority; source exact `2f60913259f9ce834ffdf75f63eef87c9563e644` remains its historical implementation baseline. The derived Refresh availability, unjoined direct retry, joined leave/join composition, request identity, button pending state, stale fences, and protected presentation/public boundaries remain authoritative except where the Owner now consolidates all connection feedback under the fixed Runtime readiness owner and narrows error presentation to logical terminal failure.

The old Owner task for a602 alone stays deferred. Implementation MAY use focused commits for reviewability, but no intermediate head may receive final Review, QA, Owner acceptance, checkout synchronization, or publication authority. Only one cumulative exact containing all seven outcomes enters gates.

The a602 Refresh request identity, availability, immediate operation dispatch, button spin, 300ms minimum visible loading dwell, error diagnostics, and stale-request fences remain authoritative with three Owner-directed refinements. First, every accepted manual Refresh and actual direct/automatic connect, join, reattach, host rebuild, or recovery SHALL converge on fixed Runtime `AppFeedback` owner `webchat-runtime-readiness`. That sole connection feedback owner SHALL display exact copy `Connected to the chat...` while active. Success SHALL dismiss only it after any accepted dwell and SHALL NOT publish `Ready to chat` or another success descriptor. Only a logically final failure, after no current automatic continuation or handoff remains capable of succeeding, SHALL replace it with exact copy `Connection failed` with no trailing period. An intermediate RPC/probe/Port/host attempt, an expired old deadline, an obsolete generation, or a retry/handoff that remains in progress SHALL retain or transfer loading ownership without displaying the terminal error.

The legacy `Toast.OnRoomSelfJoinRoomEffect` and its `SelfJoinRoomEvent -> LoadingCommand("Connected to the chat...")` random-owner producer SHALL be deleted entirely, not renamed, reused, or hidden. The independent manual-Refresh `Reconnecting to the chat...` producer SHALL also be deleted rather than mapped to another owner. No request-owned or self-join-owned second connection Toast may coexist, and unrelated Toasts remain untouched. This is a repair 6 presentation refinement, not an eighth repair.

Second, Refresh control motion SHALL derive from the sole current Runtime readiness loading owner rather than from the click event alone. That Toast entry and the existing mounted Refresh control are two projections of the same state: for every interval in which the owner is `loading`, the button SHALL be disabled and its icon SHALL rotate continuously. This includes direct/automatic connection or join, reattachment, host rebuild, recovery, manual Refresh, the accepted manual minimum dwell, and a panel mount or re-render during an already active Chat connection. It SHALL NOT create or mount a pre-App control while Runtime bootstrap is unresolved. Current success SHALL dismiss the owner and end control loading in the same transition; only logically final failure SHALL replace it with exact `Connection failed` and end control loading without hiding the error. The icon SHALL then stop and ordinary availability SHALL be recomputed: a finally failed join with otherwise valid configuration enables retry, while an unrelated static eligibility failure MAY still keep the button disabled without rotation. Stale or intermediate settlement cannot stop the animation, enable the button, or clear/replace feedback owned by a newer or continuing logical operation.

Passive polling remains outside that presentation owner. A periodic health check, provider identity probe, or watchdog observation that has not yet promoted into an actual connect, join, register/attach recovery, or host rebuild SHALL publish no loading entry and SHALL not disable or rotate Refresh. A healthy result leaves presentation unchanged. If the observation proves that repair is required, the sole readiness owner begins exactly when the lifecycle promotes into the actual recovery operation; it inherits that logical operation's valid remaining deadline rather than resetting it. Poll completion itself cannot dismiss, replace, or report the terminal result of that operation. A check suspended beyond its captured deadline, or any completion from an older check/generation, loses settlement authority before current reactivation/reconciliation work can succeed or fail.

### 2. Artico liveness is a state invariant, not a one-shot close edge

The provider adapter SHALL maintain this invariant:

> Whenever desired room demand is non-empty, the adapter owns either one non-terminal peer generation or exactly one restart capable of creating it.

On the transition from no desired room to fresh demand, `join(roomId)` SHALL inspect the current Artico signaling state. If the retained peer is `disconnected`, it SHALL enter the same single restart owner used by `close` recovery before the join waits for readiness. Concurrent Chat and World joins, a pending delayed restart, and repeated joins SHALL fan into that owner rather than create multiple peers or timers.

Every peer callback and delayed restart SHALL be generation-fenced. A stale peer's `open`, `error`, or `close`, and a stale timer, cannot join rooms, reject current work, or replace a newer peer. `leave()` and `dispose()` SHALL remove only their owned room demand; dispose SHALL cancel restart work and settle pending joins exactly once. The host-lifetime peer id remains stable across replacement peers.

This repair does not restart a merely `connecting` or `connected` peer on every join and does not add a provider watchdog. Runtime retains the bounded physical-room timeout and late-completion fences.

### 3. Supersession is a typed internal cancellation

Connection's newest-wins generation and abort of provisional Session/World state remain correct. Supersession SHALL use a machine-readable internal cancellation outcome rather than an ordinary user failure or message-string comparison.

The superseded operation SHALL settle its own caller and pending cleanup, but SHALL NOT:

- emit `Room.OnErrorEvent` or a generic error Toast;
- report success or retain its stale user/site input;
- complete join state, publish presence, or clear a newer request;
- overwrite the winning Runtime snapshot or identity.

The winning attempt alone owns the real success/failure result and convergence for every attached same-domain page. Application join/recovery status and button/request cleanup SHALL not remain loading after cancellation. Real provider, protocol, persistence, and join errors continue through existing error paths unchanged.

Logical identity binding and user projection are distinct. A bound `sessionId` cannot change `user.id`, and an accepted `presenceId` cannot change its `user.id` or `joinedAt`. For that same binding, `name` and `avatar` are mutable presentation facts rather than generation identity: an accepted refresh SHALL replace the current projection and converge it to every attached same-domain page without changing membership, allocating a generation, or emitting a join/leave notice. Repeating the same projection is idempotent. A stale superseded attempt cannot restore an older projection.

### 4. SESSION carries one logical join timestamp

The v3 Chat SESSION shape is exactly:

```ts
interface SessionMessage extends ChatSession {
  type: 'session'
  presenceId: string
  joinedAt: number
}
```

`joinedAt` SHALL be a required finite safe non-negative integer allocated and persisted by Session when it creates a new local logical presence. That persisted generation fact is the only valid local source; the wire SHALL project it unchanged. Reconnect, Refresh, reattach, duplicate publication, additional physical session, and supported Runtime host replacement reuse the same `{presenceId, joinedAt}`. SESSION_END remains exactly `{type:'session-end',presenceId}`.

The first strict remote SESSION accepted from the v3 wire binds its `user.id` and `joinedAt` to that `presenceId` in the observer ledger and records the current `name`/`avatar` projection. A duplicate or replacement SESSION for the same generation with the same `user.id` and `joinedAt` SHALL accept a changed `name` or `avatar` as the current projection, while an equal projection is idempotent; neither case changes membership or notices. A missing, malformed, or unsafe `joinedAt`, or a different `user.id` or `joinedAt` for an accepted generation, is a source-local protocol violation: the complete SESSION SHALL be dropped before membership/projection/notice mutation, while prior accepted state remains unchanged. Receiver observation time, discovery time, `baselinePeerIds`, and `clock.now()` are local metadata only and SHALL NOT supply or replace the remote logical time.

For one committed local logical generation, a remote generation is eligible for an observer-local join only when:

- its accepted `joinedAt` is strictly greater than the local generation's `joinedAt`; and
- the remote user transitions from zero active logical generations to one.

A remote timestamp less than or equal to local is historical snapshot convergence even if peer discovery and SESSION both arrive after local commit. A later remote SESSION received during a still-provisional local attempt MAY be retained as attempt-owned notice eligibility, but nothing becomes observable unless that attempt commits; superseded/rolled-back attempts emit nothing. `baselinePeerIds` may still own physical catch-up/convergence bookkeeping, but it SHALL NOT determine relative logical join order.

Equal timestamps make no claim that either generation is later. The fact is sender-asserted P2P event time and is not trusted for routing, authentication, resource admission, or global clock correctness. The accepted product behavior restores prior timestamp semantics under ordinary synchronized browser clocks; a central sequencer is outside this product.

### 5. Chat and World move together to protocol generation v3

Both physical namespace inputs SHALL change from their exact v2 values to exact v3 values. Current clients join only v3 Chat and World rooms; v1 and v2 clients remain in their own generations. No current parser receives another generation's frames, and no compatibility decoder, translator, optional field, dual join, dual send, or fallback exists.

World wire remains exactly `{sessionId,user,sites}` with no `type` or `joinedAt`. Its namespace moves solely so the cross-domain discovery list cannot count an old peer that the current Chat parser cannot communicate with. Codec algorithm, limits, Chat room derivation by origin, and World singleton ownership remain unchanged.

This protocol-generation change does not choose an application release number or update package metadata.

### 6. URL fragment is excluded from canonical page-routing identity

The content page SHALL continue to qualify from the extension manifest and the existing HTTPS/exclusion rules. A URL fragment SHALL NOT participate in content-script eligibility, Runtime domain identity, trusted tab binding, document-generation identity, or the equivalence check used to return an RPC response to the same live document. The Runtime domain remains `document.location.origin`; changing only `location.hash` SHALL NOT create a new domain, tab binding, document generation, logical presence, join, leave, or UI mount.

The background/Offscreen routing boundary SHALL retain a trusted exact tab identifier from extension-provided sender context, validate it against the background-owned Tabs API registry, and compare a canonical document-navigation identity that excludes only the fragment. Scheme, host, port, path, and query remain part of navigation identity. An old response from a genuinely replaced document, changed path/query navigation, recycled tab id, untrusted source, wrong namespace/direction, or missing target SHALL still be rejected. Response routing SHALL NOT route by origin alone, broadcast to every same-origin tab, trust a payload-supplied tab id, or remove stale-response protection. Tabs API inventory used only to reconstruct physical tab ownership is not response broadcasting.

Direct startup at `https://host/path?query#fragment`, hash-only navigation after mount, and a hash change while the initial coordinator/Runtime handshake is in flight SHALL each converge to the same page client and one mounted Shadow UI. A hash change SHALL not replace document generation, restart `initClient()`, remount the application, re-register a second page, or create logical lifecycle notices. A genuine same-domain eligible document navigation or reload SHALL replace document generation and rebind the same trusted tab without replacing its logical presence; no response owned by the old document may settle the new client. Navigation to another Runtime domain or outside eligibility SHALL release the old domain binding and cannot carry that domain's presence into the destination.

The existing product rule remains: content bootstrap mounts no alternate loading/unavailable/Retry/status UI before `initClient()`. This repair restores the valid response route; it does not turn presentation into Runtime authority or add a fallback control.

### 7. ClientLease recovery is deadline-owned and single-flight

Each ClientLease lifecycle SHALL own at most one current startup or recovery generation. The existing 15,000ms startup/recovery timeout remains the overall generation budget and SHALL start once for the current logical operation; repeated watchdog failure, generation/host-id/page-attachment mismatch, and overlapping recovery calls SHALL join that same task rather than reset its budget, restart feedback, or issue parallel attach sequences. A fresh `init()` or page-context `detach()` SHALL abort the old connectivity lifecycle and retire all of its request ownership without removing the background-owned physical tab binding. A watchdog check that was suspended beyond its captured deadline or superseded by reactivation/reconciliation SHALL not reuse its former `isCurrent` eligibility to settle HostPhase, readiness, or presentation.

Every `coordinator.registerPage()` and `server.attachPage()` attempt SHALL have a hard per-RPC deadline no greater than 5,000ms and no greater than the current logical operation's remaining valid budget. Expiry SHALL cancel that request's local ownership and reject the attempt so the existing bounded retry policy may continue only within that operation. If the transport cannot stop already-dispatched remote execution, its correlation SHALL still be retired locally. A late resolve/reject from an expired, aborted, detached, or superseded request SHALL be inert: it cannot publish ready/unavailable, replace the snapshot, start a watchdog, settle a newer generation, release the winner's tab binding, or unregister its logical lease.

Watchdog, ping, heartbeat, and Port observations SHALL remain connectivity inputs only. Their loss MAY start or join the current bounded recovery generation, but SHALL NOT remove the background's physical tab ownership, decrement the authoritative tab registry, start last-tab grace, retire logical membership, or publish SESSION_END. A poll or probe that remains observational SHALL also create no presentation loading. If it promotes into real recovery, feedback begins once at promotion and the current logical operation's valid deadline continues without reset. An old check's expired deadline is not authority to terminate newer reactivation, attach, retry, or handoff work.

A current valid attachment within the budget SHALL publish the accepted snapshot and settle `ready`. Exhaustion, loss, or rejection SHALL settle `unavailable` only when the current logical connection operation truly terminates and no current automatic continuation or handoff remains capable of succeeding; the implementation SHALL log the final cause once. Host replacement, Port disconnect, response loss, deadline expiry, Refresh, reactivation, and retry handoff remain intermediate while that logical operation continues. No recovery signal may leave HostPhase or feedback permanently connecting, but boundedness SHALL NOT grant obsolete work terminal settlement authority.

Readiness truth and presentation remain separate. Every current page Refresh or actual connect/join/reattach/host rebuild/recovery operation SHALL activate fixed owner `webchat-runtime-readiness` with exact visible copy `Connected to the chat...` when that operation starts, including attachment to a healthy retained Runtime, and SHALL keep that sole connection feedback owner current while the logical operation is active. The legacy self-join producer and independent manual-Refresh `Reconnecting to the chat...` producer SHALL both be absent. Passive polling or a health probe that has not promoted into an operation SHALL publish no entry and leave the Refresh control's ordinary state unchanged. If it promotes, feedback begins once at that transition within the current logical operation's valid deadline. Direct/automatic Chat connection and join SHALL project that same current activity to the existing Refresh control even when they are not caused by a Refresh click. For as long as the owner remains `loading`, the control SHALL remain disabled and rotating. Current ready SHALL dismiss only that owner and end its control loading without publishing `Ready to chat` or any success descriptor. Only logically final unavailable SHALL replace the same owner with exact copy `Connection failed`, end control loading, and remain visible; the underlying cause remains diagnostic rather than user-visible connection copy. Detach, remount, abort, old deadline, retry handoff, or supersession SHALL retire only obsolete operation/attempt ownership. Polling or stale settlement cannot publish transient unavailable/error, dismiss or replace the current generation's feedback, or stop its control animation. The presentation owns no Runtime/network truth and cannot extend the recovery budget. No alternate bootstrap UI, pre-App Refresh control, second connection owner, or Toast visual/structure change is added.

### 8. Tabs API owns physical tab lifetime; connectivity owns recovery only

The background coordinator SHALL own one registry from the current Runtime host generation to zero or more eligible physical browser tabs. A host may own many tabs, and each live `tabId` SHALL occur at most once in that host registry. Content-to-background comctx metadata MAY carry tab routing facts, but the background SHALL accept them only when extension-provided sender context and the current Tabs API view validate the exact tab and document binding. A page-supplied or stale tab id is never authority.

Three identities remain separate. `tabId` identifies the browser's physical tab within its supported lifetime; an internal document generation identifies the current content document and fences responses across reload or real navigation; logical `sessionId`/`presenceId`/`joinedAt` identifies membership. A tab id SHALL NOT become the logical session id, and a random page id SHALL NOT substitute for browser tab ownership. Reuse of a tab id after close, an old document message, or an old host generation SHALL be rejected without inheriting the prior logical presence.

`tabs.onRemoved` or equivalent verified tab disappearance SHALL remove the physical tab owner exactly once. Navigation outside content eligibility or to another Runtime domain SHALL release the old domain binding exactly once; an eligible destination MAY establish its own binding. Inactive, hidden, frozen, or discarded state SHALL retain the tab owner and logical presence. Hash-only navigation SHALL retain tab, document generation, and presence. Reload or same-domain eligible document navigation SHALL replace only document generation, then idempotently reattach the same tab and logical presence. Ping/Port absence remains a recoverable connectivity fact and SHALL never impersonate any of these leave events.

After supported background or Runtime host replacement, the coordinator SHALL rebuild the new host-to-tabs registry from the browser's current eligible tabs and trusted reattachments. An existing eligible tab SHALL rebind without a new logical join, notice, SESSION_END, or duplicate lease; an absent or no-longer-eligible tab SHALL not be resurrected. Registry reconstruction SHALL not create an origin-wide response route or a parallel Runtime domain lease/grace owner.

One required control SHALL suspend a passive check beyond its old deadline, resume/reactivate, accept a current attachment, retain tab binding/logical presence, and prove the obsolete completion has no HostPhase, readiness, or frontend settlement authority. Tab-lifecycle tests SHALL prove that connectivity loss cannot cause leave, trusted Tabs API events own exact removal/domain transitions, multiple tabs share one host without identity collapse, and host replacement reconstructs only current eligible bindings. Application tests SHALL include explicit parent/candidate controls for pure polling versus promoted recovery, plus parent fail-firsts proving the legacy self-join random owner can coexist with Runtime readiness, manual Refresh independently emits `Reconnecting to the chat...`, an old suspended check can flash unavailable before the next watchdog succeeds, both-late discovery plus historical SESSION currently persists a pre-join peer notice, direct connection Toast loading does not project the required disabled rotating Refresh control when the existing control is mounted, a direct fragment URL does not mount the application, and missing page health currently can release a tab that still exists. Candidate controls SHALL prove both duplicate connection producers are absent, exactly one fixed owner carries loading `Connected to the chat...` and terminal `Connection failed`, polling creates no Toast/control loading, promotion begins both once without deadline reset, Toast loading and mounted Refresh control loading never diverge, manual and direct/automatic loading share the current mounted control state, every ultimately successful initial/manual/reactivation/reattach/recovery flow has zero transient error, success dismisses only the sole owner without a success descriptor, only logical final failure replaces it with the exact terminal copy, stale completion cannot end newer animation or settle readiness, exact A-before-B notice projections are A `[A joined, B joined]` and B `[B joined]`, the full fragment routing matrix passes, and physical tab leave occurs only from trusted browser lifecycle facts. ## Risks / Trade-offs

- [Sender clocks can be skewed] -> Document `joinedAt` as sender-asserted observer-notice ordering only; do not use it as a security or transport fact. Strictly greater preserves the prior product rule, while a trusted global sequencer remains out of scope.
- [Required SESSION field breaks v2] -> Move Chat and World together to v3 and make isolation explicit; do not run mixed parsers in one room.
- [Join-driven restart could create peer churn] -> Trigger only for a terminal `disconnected` peer and converge close-driven/join-driven work through one restart owner.
- [Cancellation suppression could hide real failures] -> Use a machine-classified supersession outcome only; all other failure kinds retain current error feedback.
- [Seven repairs increase candidate scope] -> Keep implementation boundaries focused, require direct and cumulative scope evidence, and gate only one final exact as explicitly requested.
- [Removing URL equality could route a response to the wrong document] -> Canonicalize only the fragment while retaining trusted tab id plus scheme/host/port/path/query equality and generation-local response correlation.
- [A deadline can reject a genuinely slow but live control plane] -> Keep the existing 15-second overall logical-operation budget and cap individual calls at 5 seconds to permit bounded retry, but show `Connection failed` only after the logical operation truly terminates without a current continuation or handoff; do not let an old captured deadline impersonate that result.
- [A stale readiness operation can outlive or overwrite a newer recovery] -> Keep one fixed feedback owner with operation-, attempt-, watchdog-, deadline-, and generation-fenced settlement; retire obsolete ownership on every lifecycle replacement and fence every late settlement from HostPhase, readiness, and presentation.
- [A connectivity signal can falsely remove a still-open tab] -> Make trusted Tabs API lifetime the only physical tab-removal authority; ping, heartbeat, Port, visibility, freeze, and discard remain health inputs only.
- [A tab id can be stale, spoofed, or reused] -> Validate comctx metadata against extension sender context and the current host registry, fence document/host generations, and never reuse tab id as logical session identity.
